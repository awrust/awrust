# ADR-0007: Ship awrust CLI in the Docker image, remove curl

## Status
Accepted (supersedes [ADR-0001](ADR-0001.md))

## Context
Init scripts needed an HTTP client to provision resources at startup. ADR-0001 chose curl for this role. The awrust project now has a dedicated CLI (`awr`) that speaks the S3 API natively, reads `AWRUST_ENDPOINT` from the environment, and covers every operation init scripts need.

Shipping a generic HTTP client for a problem that has a purpose-built tool is unnecessary indirection.

## Decision
Build `awr` from source in a parallel Docker build stage and include it in the image. Remove `curl` from the runtime image.

## Alternatives considered
- **Download pre-built CLI binary**: The release artifacts target glibc (`*-unknown-linux-gnu`). The runtime image is Alpine (musl). Incompatible without a compatibility shim.
- **Keep curl alongside awr**: Preserves a tool that no longer has a purpose in the image. Extra surface area for no gain.

## Consequences
Positive:
- Init scripts use `awr s3 mb my-bucket` instead of raw `curl -X PUT` — intent is explicit
- CLI reads `AWRUST_ENDPOINT` natively — no URL construction in shell scripts
- One fewer runtime dependency to track for security patches (libcurl)

Negative:
- CLI build stage adds time to Docker image builds (mitigated by BuildKit parallelism)
- Image size is roughly neutral: curl + libcurl (~8 MB) replaced by a statically-linked Rust binary of comparable size
- Users who relied on curl in init scripts for non-awrust HTTP calls must extend the image
