# ADR-0003: Hyper as HTTP layer instead of a framework

## Status
Accepted

## Context
awrust's facade is a reverse proxy, not a web application. Its HTTP requirements are:
1. Accept inbound connections with HTTP/1.1 and HTTP/2 support
2. Inspect headers to determine the target service (routing)
3. Forward the entire request — including the body — to a backend without buffering
4. Stream the backend's response back to the client without buffering

A reverse proxy must treat the request body as an opaque byte stream. Frameworks like axum or actix-web are designed for request handlers that consume and deserialize bodies — the opposite of what we need.

## Decision
Use hyper 1.x directly (with hyper-util for connection management and http-body-util for body type conversions) as the HTTP layer. No framework.

## Alternatives considered
- **axum**: Built on hyper and Tokio, it would give us routing macros and middleware. But axum's Router owns request deserialization and body extraction. To proxy without buffering, we would need to bypass axum's handler model and call into hyper directly — gaining the dependency but not the ergonomics.
- **actix-web**: Uses its own runtime (actix-rt, which wraps Tokio). Body forwarding requires converting between actix's Payload and hyper's Incoming — an impedance mismatch that adds allocations on every request. The framework's middleware, guards, and extractors go unused in a proxy.
- **warp**: Filter-based composition is elegant for REST APIs but has no escape hatch for raw connection-level control. Warp internally uses hyper but hides the connection accept loop, which we need to own for graceful shutdown and per-connection spawning.
- **reqwest (client only)**: Could replace hyper-util's Client for forwarding, but reqwest buffers responses by default and does not expose the streaming Incoming body type. We would lose zero-copy proxying.

## Consequences
Positive:
- Zero-copy body forwarding: `Request<Incoming>` goes in, URI is rewritten, `Client::request` sends it out — no intermediate buffering
- Full control over the accept loop (`tokio::select!` for shutdown), connection lifecycle, and HTTP version negotiation
- Minimal API surface to learn — `service_fn`, `Builder`, `Client` — because the proxy's logic is simple
- ~15 direct + transitive crates vs. ~80+ for axum or actix-web

Negative:
- No built-in router, middleware, or error handling — we write `route()`, `handle()`, and `service_unavailable()` by hand
- hyper 1.x split the API across three crates (hyper, hyper-util, http-body-util), which increases the cognitive load of reading dependency declarations
- Upgrading hyper major versions requires updating all three crates in lockstep
