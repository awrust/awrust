# ADR-0001: Include curl in the Docker image

## Status
Accepted

## Context
AWRust now supports init scripts — shell scripts in `/etc/awrust/init/ready.d/` that run after all services are healthy, allowing users to provision resources (buckets, queues, etc.) without a sidecar container.

These scripts need an HTTP client to talk to the facade endpoint. The Alpine base image ships only BusyBox `wget`, which cannot issue PUT requests — the HTTP method required by S3's CreateBucket and PutObject APIs.

## Decision
Install `curl` via `apk add --no-cache curl` in the runtime stage of the Dockerfile.

## Alternatives considered
- **BusyBox wget (no change)**: Cannot do PUT/POST with body. Users would be unable to provision S3 resources from init scripts, defeating the feature's purpose.
- **GNU wget (`apk add wget`)**: Supports `--method=PUT` and is smaller (~2 MB vs ~8 MB). However, curl is the de-facto standard for HTTP scripting, has richer S3-compatible options (`-T`, `-H`, `--data-binary`), and is what users will reach for first.
- **AWS CLI**: The authoritative tool for S3 operations, but adds ~150 MB+ and Python to a minimal Alpine image. Users who need it can extend the image themselves.
- **No HTTP client (marker-file-only scripts)**: Would limit init scripts to filesystem operations, making the feature far less useful.

## Consequences
Positive:
- Init scripts can provision any AWS resource out of the box
- Matches user expectations — curl is the most common HTTP tool in shell scripts
- BDD integration tests work in both cargo and Docker modes without conditional logic

Negative:
- Adds ~8 MB to the image (curl + libcurl + dependencies)
- Introduces a runtime dependency that must be kept updated for security patches
