# ADR-0006: Hyper for the facade, Axum for services — no forced standardization

## Status
Accepted

## Context
The awrust workspace contains two kinds of binaries with opposing HTTP requirements:

1. **The facade** (this crate) is a reverse proxy. It inspects request headers to pick a target, rewrites the URI, and forwards the request body as an opaque byte stream. It never reads, parses, or buffers the body.

2. **Service emulators** (e.g. awrust-s3) are web applications. They route by path and method, extract path segments and query parameters, consume and deserialize request bodies, and build typed responses.

The facade chose hyper directly (ADR-0003). awrust-s3 chose Axum (awrust/awrust-s3 ADR-0002). The question is whether both projects should standardize on one HTTP layer.

## Decision
Each binary uses the HTTP layer that fits its role. The facade uses hyper; service emulators use Axum. There is no mandate to unify.

## Alternatives considered
- **Axum everywhere**: The facade would need to work around Axum's handler model, which consumes the request body via extractors. Zero-copy proxying requires holding the raw `Request<Incoming>` and passing it to hyper's `Client::request` — exactly what Axum's design discourages. We would carry a framework dependency that we actively bypass.
- **Hyper everywhere**: Service emulators would hand-roll routing, path extraction, query parsing, and error mapping — reimplementing what Axum provides. Every new service would duplicate this boilerplate or grow an internal micro-framework that converges on Axum anyway.
- **Shared internal HTTP crate**: An abstraction that wraps both use cases would need to be transparent enough for proxying and ergonomic enough for application handlers. This is the exact design space that Axum and hyper already occupy — building a third option is duplication, not unification.

## Consequences
Positive:
- Each binary uses the minimal, correct abstraction for its role
- No framework overhead in the hot path of the reverse proxy
- No boilerplate overhead in service emulators
- Axum is built on hyper — the ecosystem is shared (tokio, http, hyper types) even if the API surface differs

Negative:
- Contributors must understand two HTTP programming models
- Dependency trees diverge slightly (Axum pulls in matchit, tower, tower-http, etc.)
- A hypothetical service that needs raw streaming would need to justify Axum vs. hyper for its specific case
