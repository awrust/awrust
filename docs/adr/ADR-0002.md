# ADR-0002: Tokio as async runtime

## Status
Accepted

## Context
AWRust is a process manager and reverse proxy that must handle thousands of concurrent connections, spawn and supervise child processes, listen on TCP and UDP sockets, and react to OS signals — all without blocking. The choice of async runtime is the single most load-bearing dependency decision because every other crate must integrate with it.

## Decision
Use Tokio with the multi-threaded scheduler (`rt-multi-thread`) as the sole async runtime.

## Alternatives considered
- **async-std**: Smaller community, fewer integrations. hyper — the HTTP library we need — is built on Tokio. Using async-std would mean either forking hyper's I/O layer or adding a compatibility shim, both of which add complexity for no gain.
- **smol**: Minimal by design, which is appealing, but lacks first-class process management (`tokio::process`), signal handling (`tokio::signal`), and timed operations (`tokio::time`). We would need to pull in separate crates for each, re-assembling what Tokio already provides as a coherent whole.
- **Raw threads + epoll/kqueue**: Eliminates the runtime dependency entirely but requires writing our own event loop, timer wheel, and task scheduler. The facade's accept loop, DNS responder, init-script runner, and health checks all run concurrently — hand-rolling this is a project unto itself.

## Consequences
Positive:
- Native integration with hyper, hyper-util, and tracing — no glue code
- `tokio::process` gives us async child-process supervision with inherited stdio
- `tokio::signal::ctrl_c()` provides clean shutdown without raw signal handling
- `tokio::time::timeout` and `tokio::time::sleep` are available everywhere (DNS forwarding, health polling, init scripts)
- The ecosystem default — any future crate we pull in will almost certainly support Tokio

Negative:
- Large dependency tree (~70 transitive crates) for a project that otherwise keeps dependencies minimal
- The multi-threaded scheduler adds complexity we may not need at current scale, but switching to `current_thread` is a one-line change if profiling warrants it
